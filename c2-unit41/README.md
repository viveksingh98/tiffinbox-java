# c2-unit41 — Stream Gatherers: Custom Pipeline Steps (JDK 25.0.4.1)
Run the two compact source files directly, **with no flags at all**: `java Gather.java` · `java Custom.java`. Gatherers went final in JDK 24 (JEP 485), so `--enable-preview` is neither needed nor harmful — it is simply ignored, and the output is byte-identical either way.
`Gather.java` — the four built-ins over Asha's seven days `240, 150, 300, 120, 240, 150, 300`: `windowFixed(3)` (note the **short final window** `[300]`), `windowSliding(3)` (five windows, `n - size + 1`), `scan` (the running total), and `fold` over the four anchor customers, which recomputes Unit 08's `24300`. 6 runs, byte-identical, md5 `18c933e3…`, exit 0, empty stderr.
`Custom.java` — a seven-line `Gatherer.ofSequential` with `int[1]` state whose integrator returns `false` to short-circuit: budget 800 lets three orders through and a `peek` counter proves the source produced only **4 of 6** elements; the same gatherer terminates an **infinite** `Stream.iterate`; and `mapConcurrent(4, …)` shows virtual threads preserving encounter order. 6 runs, byte-identical, md5 `775cae27…`, exit 0.
Check the API yourself: `javap java.util.stream.Gatherers` lists exactly five factories with no preview marker; `javap 'java.util.stream.Gatherer$Integrator'` shows `integrate(...)` returns `boolean`, while `javap java.util.stream.Collector` shows `accumulator()` returns a `BiConsumer` — that is why a collector can never short-circuit.
`ParProbe.java` — the proof behind the Slide 5 claim: the same gatherer over a 2,000-element `parallelStream()`, collecting the name of every thread that enters the integrator. One thread, in order, on every run — `ofSequential` really does refuse to parallelise.
