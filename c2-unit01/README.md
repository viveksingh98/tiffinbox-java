# Core Java II — Unit 01 — Stack vs Heap: Where Your Objects Actually Live

- `StackVsHeap.java` — `record Customer(String name, int mealsPerDay)` + `int bill(Customer c, int price)`; `days`, `price` and the reference `c` live in `bill`'s stack frame, the `Customer` object lives on the heap. Prints `Customer[name=Ravi, mealsPerDay=2] -> 7200` / `same object? true`. Run: `java StackVsHeap.java`
- `MemoryMap.java` — reads `Runtime.maxMemory()` / `totalMemory()` / `freeMemory()` / `availableProcessors()`. Run compiled so the numbers are the same on every run: `javac -d out MemoryMap.java && java -Xmx64m -cp out MemoryMap` → `Max heap: 64 MB` / `Total heap: 64 MB` / `Free heap: 61 MB` / `Used heap: 2 MB` / `CPU cores: 8`. With no `-Xmx` the max is a quarter of your RAM (`MaxRAMPercentage = 25`); with `java MemoryMap.java` the source launcher's compiler shares the heap and "used" reads about 14-15 MB.
- `Deep.java` — infinite recursion caught as `StackOverflowError`, printing the depth reached. Run: `java Deep.java` — the count **changes every run** (17640 … 55473 across ten runs here) because the JIT recompiles `dive()` mid-flight; `java -Xint Deep.java` (interpreter only) prints `17640` every time and `java -Xss256k Deep.java` prints `stack overflowed after 1256 calls` every time.
- Default flags on this machine, from `java -XX:+PrintFlagsFinal -version`: `MaxHeapSize = 4294967296`, `MaxRAMPercentage = 25`, `ThreadStackSize = 2048` (KB).
- Needs JDK 25 (compact source files + `IO.println`, JEP 512). Verified on JDK 25.0.4.1 (macOS, Apple silicon, 8 cores, 16 GB).
