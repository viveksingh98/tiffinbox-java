# Core Java II — Unit 02 — Heap Limits: -Xmx, OutOfMemoryError and Heap Dumps

- `Overflow.java` — an `ArrayList<byte[]>` that adds one megabyte per "order" and never removes it. Compile first so the source launcher's compiler does not share the tiny heap: `javac -d out Overflow.java && java -Xmx16m -cp out Overflow` → `holding 1 MB` … `holding 6 MB`, then `Exception in thread "main" java.lang.OutOfMemoryError: Java heap space` with the top frame `java.base/jdk.internal.misc.Unsafe.allocateUninitializedArray0` under `StringConcatHelper.newArray` — the *string concatenation* for the next print is the allocation that fails. Identical on 3 runs. `-Xmx32m` → `holding 14 MB`; `-Xmx64m` → `holding 30 MB`.
- Why 6 and not 16: `java -Xmx16m -Xlog:gc+heap=info -cp out Overflow` → `GC(2) Humongous regions: 12->12` / `GC(5) Humongous regions: 14->14` (identical on 3 runs). `G1HeapRegionSize = 1048576`, so a `new byte[1024*1024]` (1 MB + header) is *humongous* and takes **two** regions; 7 arrays = 14 of the 16 regions. Same arithmetic at `-Xmx32m`: `Humongous regions: 30->30` of 32.
- Heap dump: `java -Xmx16m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=dump.hprof -cp out Overflow` → `Dumping heap to dump.hprof ...` / `Heap dump file created [11247086 bytes in 0.018 secs]`. The **byte count follows what the heap was holding** (it changes with the program and the `-Xmx`) and the seconds change every run — never quote either as a fixed fact. Open the `.hprof` in VisualVM (free, visualvm.github.io) or IntelliJ Ultimate.
- `OrderHistory.java` (leak) vs `BoundedHistory.java` (fix, one extra line `if (history.size() > 10) history.removeFirst();`) — both `javac -d out X.java && java -Xmx64m -cp out X`. Leak: `day 1: history holds 10 orders, 21 MB used` / `20 orders, 41 MB` / `30 orders, 61 MB` / then `OutOfMemoryError` on day 4. Bounded: `10 orders, 21 MB used` on all four days. Identical on 3 runs each (each `usedMB()` calls `System.gc()` first so the number is the live set, not garbage).
- `Hold.java` — holds 20 MB and sleeps, so you can inspect a *running* JVM. `javac -d out Hold.java && java -Xms64m -Xmx64m -cp out Hold &` then `jcmd -l` for the pid, `jcmd <pid> VM.flags | tr ' ' '\n' | grep HeapSize` → `-XX:InitialHeapSize=67108864` / `-XX:MaxHeapSize=67108864` / `-XX:MinHeapSize=67108864` / `-XX:SoftMaxHeapSize=67108864`, and `jcmd <pid> GC.heap_info` → `garbage-first heap total reserved 65536K, committed 65536K, used 42836K` / ` region size 1024K, 2 young (2048K), 1 survivors (1024K)` (`used` moves while the app runs).
- Defaults on this machine, from `java -XX:+PrintFlagsFinal -version`: `MaxHeapSize = 4294967296` (4096 MB), `MaxRAMPercentage = 25`, `G1HeapRegionSize = 1048576`, `UseG1GC = true`.
- Needs JDK 25 (compact source files + `IO.println`, JEP 512). Verified on JDK 25.0.4.1 (macOS, Apple silicon, 8 cores, 16 GB).
